# Review: DriftGuard

## Verdict: FIX-FIRST

Core parsing, normalization, comparison, and CLI output all work. TypeScript typechecks clean. All 108 tests pass. However, several contract violations produce wrong output, the MCP incremental-cache architecture is broken as wired, and CI will fail on the lint step from day one.

---

## Findings

### CRITICAL

- **[CRITICAL] package.json:devDependencies - `eslint` is not listed as a devDependency, and `@typescript-eslint/parser` / `@typescript-eslint/eslint-plugin` are not in devDependencies or node_modules.** The CI workflow runs `npm run lint` (eslint src tests --ext .ts) and `.eslintrc.json` references these plugins. `npm run lint` fails immediately with "eslint is not recognized". Fix: add `eslint`, `@typescript-eslint/parser`, `@typescript-eslint/eslint-plugin` to devDependencies.

### HIGH

- **[HIGH] src/mcp/watch.ts + src/mcp/server.ts - Watcher entity map is never used by MCP tool handlers.** `createWatcher()` returns a `Watcher` with `getEntityMap()` and keeps an incrementally-updated `EntityMap` in `context.entityMap`. But `handleCheckDrift`, `handleGetEntityMap`, and `handleListEntities` all call `buildEntityMap(config)` directly, bypassing the watcher entirely. Every MCP tool call re-parses all source files from scratch. The sub-50ms incremental latency described in architecture.md is impossible as implemented. Fix: pass the `Watcher` instance into tool handlers and call `watcher.getEntityMap()` instead of `buildEntityMap(config)`.

- **[HIGH] src/mcp/watch.ts:40-45 - TypeScript source files are not watched.** `pathsToWatch` includes `config.prisma`, `config.openapi`, and `config.typescript.tsconfig` - but NOT the actual TS source files from `config.typescript.include`. Changes to TypeScript interface files will never trigger a re-parse in MCP server mode. Fix: after initial parse, collect all TS source file paths from the entity map and add them to the watcher.

- **[HIGH] src/index.ts:229-249 (checkEntity) - summary.byKind and summary.byEntity are not recalculated after filtering.** `checkEntity` spreads `full.summary` and only overwrites `total`, `errors`, `warnings`. The `byKind` and `byEntity` fields in the returned report still reflect the full unfiltered run, not the single-entity scope. Any consumer computing "how many type-mismatch issues for User?" from the returned report gets wrong counts. Fix: rebuild `byKind` and `byEntity` from `filteredIssues` before returning.

- **[HIGH] src/cli/check.ts:96-102 - Severity filter does not update the summary.** After filtering `report.issues` by severity, the report is spread with the new `issues` slice but `report.summary` is never updated. `summary.total` diverges from `issues.length` in the JSON output. Fix: recalculate `summary.total`, `errors`, `warnings` after the severity filter (same pattern as the `--entity` filter block above it).

- **[HIGH] src/index.ts:50 - `--no-cache` flag is silently ignored.** `buildEntityMap` hardcodes `const useCache = true`. The `--cache` / `--no-cache` CLI flag is wired through `CheckCommandOptions.cache` but `runCheck` never passes it to the engine. Users who pass `--no-cache` receive stale cached results. Fix: thread `config.cache` (or a runtime option) through to `buildEntityMap`.

- **[HIGH] src/mcp/server.ts:176-180 - SSE transport POST handler discards the request body.** The handler responds `200 OK` without forwarding the request to the `SSEServerTransport`. MCP clients send tool-call messages via POST `/message`; those messages are silently dropped, so the SSE transport is non-functional. Fix: call `transport.handleRequest(req, res)` (or the equivalent SDK method) inside the POST branch.

### MEDIUM

- **[MEDIUM] src/config/loader.ts:104-114 (deepMerge) - Function is a shallow merge, not a deep merge.** If a user's `driftguard.config.json` sets `typescript.exclude: ["**/*.spec.ts"]` and they also pass `--tsconfig ./tsconfig.prod.json`, the override object built in `check.ts` is `{ typescript: { tsconfig: "..." } }`. The shallow merge replaces the entire `typescript` object, losing `exclude` from the config file. Zod re-applies defaults (which restores the default exclude list), so the practical impact is limited, but a user who deliberately removed `spec.ts` from exclude would see their setting silently overwritten. The function is also misleadingly named. Fix: deep-merge the `typescript` sub-object explicitly, or rename to `shallowMerge` with clear JSDoc.

- **[MEDIUM] .github/action-entrypoint.sh:11-24 - Unquoted variable expansion allows word-splitting on paths with spaces.** `ARGS="$ARGS --config $DRIFTGUARD_CONFIG"` will break if the config path contains spaces. While GitHub Actions inputs are set by workflow authors, the safe practice is to always quote: `ARGS="$ARGS --config \"$DRIFTGUARD_CONFIG\""`.

- **[MEDIUM] src/index.ts:168-189 - check() swallows parse errors silently.** The architecture API contract states "Never throws; parse errors become DriftIssue entries with kind `parse-error`." The implementation returns an empty `issues` array with `exitCode: 1`. Consumers get no indication of what went wrong - the `DriftIssueKind` type does not include `"parse-error"`. At minimum the error message should be exposed; at full conformance a synthetic DriftIssue should be emitted. Fix: add `"parse-error"` to `DriftIssueKind` and emit a synthetic issue with the parse error message, or document the deviation from the contract.

- **[MEDIUM] src/mcp/tools/list-entities.ts:23-27 - Double parse in list_entities.** `handleListEntities` calls `buildEntityMap(config)` and `check(config)` in parallel. `check()` internally calls `buildEntityMap()` again - so two full entity maps are built per `list_entities` invocation. Even with the cache, TypeScript parsing via ts-morph runs twice. Fix: call `checkEntity` or restructure so a single `buildEntityMap` result feeds the drift check.

- **[MEDIUM] tests/integration/check.test.ts - TypeScript parsing is never exercised in integration tests on Windows.** `include: [join(fixturesDir, fixture, "types.ts")]` produces an absolute Windows path with backslashes (e.g., `C:\Users\...\types.ts`). fast-glob does not accept backslash paths as glob patterns. The test output confirms this: four "no TypeScript source files matched" warnings appear. The integration tests run only Prisma + OpenAPI comparison. Fix: convert to a relative or forward-slash path, or use `fg.convertPathToPattern()`.

### LOW

- **[LOW] src/cli/report/color.ts - Dead code, never imported.** `text.ts` implements its own inline color system. `color.ts` exports `style()` and `c.*` helpers but nothing imports them. Either adopt `color.ts` in `text.ts` (removing the duplication) or delete it.

- **[LOW] src/cache/index.ts:3 - Unused imports.** `readFile` and `writeFile` are imported from `"fs"` (sync versions) but never called. The async counterparts from `fs/promises` are used correctly. Fix: remove the dead imports.

- **[LOW] src/config/discovery.ts:24 - Unused `root` variable.** `const root = dirname(dir) === dir ? dir : null` is assigned but never read. Fix: delete the line.

- **[LOW] src/config/loader.ts:73-82 - jiti v2 compatibility path is dead code.** `package.json` pins `"jiti": "^1.21.6"` (semver range stays within v1). The `jitiModule.createJiti` branch will never execute. Remove or update the comment.

- **[LOW] tsup.config.ts:15-17 - Shebang banner applied to library entry.** `banner: { js: "#!/usr/bin/env node" }` adds the shebang to both `dist/index.js` (library) and `dist/cli/index.js` (CLI). Node.js treats `#!` as a valid hashbang comment so imports work, but bundlers (webpack, rollup) may warn. Fix: use separate tsup configs or a post-build script that adds the shebang only to `dist/cli/index.js`.

## Architecture assessment

**Core engine (canonical types, normalizer, comparator):** Solid. The discriminated union for `CanonicalType`, the three-source normalization table, and the O(entities * fields) comparator are all implemented correctly and match the design. The ignore-pattern and severity-level systems work.

**MCP incremental caching is architecturally broken.** The watcher correctly maintains an up-to-date `EntityMap` in memory, but zero tool handlers call `watcher.getEntityMap()`. The result is that `driftguard serve` performs a cold re-parse on every single tool invocation - the same cost as running `driftguard check` each time, with the added overhead of a long-lived process. This is the biggest gap between the architecture doc and the implementation.

**Config loading:** The auto-discovery + zod validation pipeline is well-structured. The `deepMerge` naming is misleading but the behavior is documented in comments. The jiti v1/v2 dual-path is unnecessary overhead.

**Scalability:** The stateless design for `driftguard check` is correct and will scale as described. The GitHub Action and CI integration are correct. The cache keying by sha256(fileContent) is sound.

**Test quality:** Unit tests are thorough for the engine layer (normalizer, comparator, discovery, loader). Integration tests exist but are de-facto only testing Prisma + OpenAPI on Windows due to the glob path bug. The `simple` fixture has an `expected-report.json` but no test reads it - that fixture is never exercised in integration.

**Dead code:** `color.ts` (full module), `parsers/index.ts` (re-export barrel never imported).

**Tight coupling risk:** `handleListEntities` and the check logic are tightly coupled - list_entities triggers a full check just to populate `hasDrift`. A lightweight "does this entity have any slots with presentIn >= 2?" check would suffice.
