## Verdict: FIX-FIRST

## Findings

### [CRITICAL]

- **[CRITICAL] output/api/ — wrong root directory; backend artifact must not ship**
  Backend engineer wrote the entire package to `output/api/` instead of the architecture-specified `output/`. The frontend engineer wrote the canonical package to `output/` (correct). Both paths now contain a full, independently installable `pinpoint` package with divergent implementations. If a user or CI step runs `pipx install ./output/api` they get a different (and in places broken) version. The `output/api/` directory must be removed or clearly quarantined before release.
  **Fix:** Delete or move `output/api/` to a `scratch/` or `archive/` folder. Only `output/` ships.

---

### [HIGH]

- **[HIGH] output/pinpoint/fetcher/__init__.py:14 — `get_dependency_info` signature deviates from architecture contract**
  Architecture contract (source of truth) specifies:
  `get_dependency_info(package: str, ecosystem: str, installed: str) -> DependencyInfo`
  The canonical package (`output/`) implements:
  `get_dependency_info(package: str, ecosystem: str, installed: str, root: Path) -> DependencyInfo`
  The extra `root` parameter was added so the fetcher can auto-discover the installed version. This is internally consistent — `output/pinpoint/pipeline.py` passes 4 args and `output/pinpoint/fetcher/__init__.py` accepts 4 args — but it breaks any code written against the published contract. The backend (now abandoned in `output/api/`) implements the 3-param version correctly.
  **Fix:** Either (a) update the architecture contract to document the `root` param, or (b) revert to the 3-param signature and move installed-version discovery into the pipeline before the `get_dependency_info` call (as the backend did with `get_installed_version`).

- **[HIGH] output/pinpoint/config.py:51-55 — API key accepted from .pinpoint.json (security)**
  Architecture explicitly states: "`anthropic_key` is NOT stored in config — must come from `ANTHROPIC_API_KEY` env var." The implementation reads the JSON file into `raw` without stripping `anthropic_key` first, then only sets the env-var value if it is non-empty. If `ANTHROPIC_API_KEY` is absent from the environment but a user has placed the key in `.pinpoint.json`, the file value is silently accepted. `test_config.py:51-62` confirms and documents this behavior (the test comment acknowledges it). Risk: a user who "shortcuts" by putting the key in `.pinpoint.json` and then commits that file will leak credentials.
  **Fix:** Add `raw.pop("anthropic_key", None)` immediately after loading the JSON, before inserting the env-var value.

### [MEDIUM]

- **[MEDIUM] output/pinpoint/pipeline.py:53-55 — LLM error silently drops package from results**
  When `get_verdict` raises `LLMError`, `_process_package` returns `None`. The package disappears from the final verdict list with no message to the user. The architecture and backend-notes both specify: "LLMError → emit a safe-default `ClaudeVerdict` (risk `"none"`) so the scan always completes rather than aborting mid-run." Silent omission is worse than a conservative "none" — the user cannot tell whether a package was analyzed and safe, or whether analysis failed.
  **Fix:** Replace `except LLMError: return None` with construction of a fallback `ClaudeVerdict(risk_level="none", ..., summary="LLM analysis failed: {exc}")` and continue to the `FinalVerdict` assembly.

- **[MEDIUM] output/api/pinpoint/models.py:44 — `DependencyInfo.changelog_text` has no default (required field)**
  In the backend model, `changelog_text: str` is required with no default. In the canonical frontend model it is `changelog_text: str = ""`. `test_pipeline.py:59-64` constructs `DependencyInfo(package=..., ecosystem=..., installed=..., latest=...)` without supplying `changelog_text`. This test passes under the canonical `output/` package but would raise a Pydantic `ValidationError` if run against `output/api/`. This is a cross-package inconsistency that would surface if the backend tests are run against the wrong package. Not a runtime bug in the deliverable, but a latent inconsistency if the backend package is ever reconciled.
  **Fix:** After `output/api/` is removed, this becomes moot. Until then, add `changelog_text: str = ""` to the backend model.

- **[MEDIUM] output/api/pinpoint/pipeline.py:72 — dead `if False else` expression**
  The line `risk_level="unknown" if False else "none"` is a no-op: the condition is a constant `False`, so it always evaluates to `"none"`. This appears to be a leftover from an abandoned refactor that intended to use `"unknown"` as the LLM-failure risk level. The code is syntactically harmless but misleading — a future reader will spend time trying to understand when the `"unknown"` branch would fire.
  **Fix:** Replace with `risk_level="none"`. (Moot if `output/api/` is deleted.)

### [LOW]

- **[LOW] output/api/pinpoint/report.py:26 — `_MIN_RISK_THRESHOLD` dict is dead code**
  `_MIN_RISK_THRESHOLD = {"none": 3, "low": 2, "medium": 1, "high": 0}` is defined at module level but never referenced. The filtering logic in `_above_min_risk` uses `_RISK_ORDER` directly. (Moot if `output/api/` is deleted.)
  **Fix:** Delete the dead dict.

- **[LOW] output/ and output/api/ — incompatible tree-sitter version pins**
  `output/pyproject.toml` pins `tree-sitter>=0.23.0` (v2 API: `Parser(Language(grammar.language()))`). `output/api/pyproject.toml` pins `tree-sitter>=0.21.0,<0.22.0` (v1 API). These are binary-incompatible. In an environment with both packages installed (e.g., editable installs for development), only one can be present, so the other package will fail at import time. Resolved by removing `output/api/`.

- **[LOW] output/api/pinpoint/scanner/js_scanner.py:91-93 — JS scanner returns empty dict silently when tree-sitter is unavailable**
  `if not _TS_AVAILABLE: return {}` — the backend's JS scanner silently yields zero imports if the tree-sitter native extension is not installed. The canonical frontend scanner has a full regex fallback. Since the deliverable is `output/`, this does not affect users, but it means the backend tests cannot detect JS imports without native tree-sitter.

- **[LOW] Fake API keys in test fixtures are syntactically valid key prefixes**
  `conftest.py` uses `"sk-ant-test-key"` and `test_config.py` uses `"sk-ant-testkey"`, `"sk-ant-from-file"`, `"sk-ant-env"`. These match the `sk-ant-` prefix pattern of real Anthropic keys. Not actual secrets (they are clearly fake), but static analysis tools may flag them. Recommend suffixing with `_NOT_REAL` or wrapping in a env-var mock that does not embed the pattern.
