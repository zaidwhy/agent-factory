# Architecture: DriftGuard

---

## Stack

| Layer | Choice | Why | Pinned Range |
|---|---|---|---|
| Runtime | Node.js 20 LTS | LTS support through 2026-04-30, native ESM, `--watch` flag | `>=20.0.0 <22` |
| Language | TypeScript 5.5 | satisfies operator for type-safe config, const type params | `^5.5.0` |
| Prisma parser | `@prisma/internals` | Official AST, no DB connection needed, stable DMMF output | `^5.22.0` |
| OpenAPI parser | `@redocly/openapi-core` | Handles multi-file $ref resolution, OpenAPI 3.0 + 3.1 | `^1.25.0` |
| TypeScript AST | `ts-morph` | High-level TS AST traversal, respects tsconfig.json paths | `^23.0.0` |
| CLI framework | `commander` | Industry standard, sub-commands, typed options | `^12.0.0` |
| Internal validation | `zod` | Config file parsing + canonical type runtime representation | `^3.23.0` |
| MCP server | `@modelcontextprotocol/sdk` | Anthropic's official SDK, stdio + SSE transports | `^1.10.0` |
| File watching | `chokidar` | Cross-platform, used by Vite/Jest, reliable on Windows | `^4.0.0` |
| Test runner | `vitest` | ESM-native, no transpile overhead, compatible with ts-morph | `^2.1.0` |
| Build | `tsup` | esbuild-backed, single config, produces CJS + ESM dual output | `^8.0.0` |
| Formatting | `prettier` | Standardized formatting | `^3.3.0` |

**Weak decision challenged:** The idea lists zod schema extraction as a peer of TypeScript interface extraction. Zod schema shapes cannot be reliably extracted from static AST analysis - the zod DSL is a fluent builder that requires runtime evaluation or a custom recursive AST interpreter. For MVP, the TypeScript parser targets `interface` declarations and `type` aliases only. Zod support ships as a follow-on after interface coverage is proven stable. This is documented in the README.

## Scalability notes

**Current (MVP - individual developer CLI):**
The tool is entirely stateless. Every `driftguard check` parses from disk and exits. No daemon, no state file. Cold parse of a 500-file TypeScript project with ts-morph takes 2-4s. Acceptable for a pre-commit hook or CI step.

**MCP server mode (watch + cache):**
When running as an MCP server (`driftguard serve`), the entity map is held in memory. `chokidar` watches the three source files (prisma schema, openapi spec, tsconfig-included TS files). On change, only the affected parser re-runs, merging into the cached entity map. Drift re-computation is O(entities * fields) - negligible. This keeps MCP tool call latency under 50ms for incremental checks.

**Caching strategy:**
- Keyed by `sha256(fileContent)` per source file
- Cache stored in `node_modules/.cache/driftguard/` (follows Webpack/Babel precedent)
- Cache invalidated on `@prisma/internals`, `@redocly/openapi-core`, or `ts-morph` version change (stored in cache manifest)
- For CI: cache directory is typically already cached by CI runners; no extra setup needed

**10x load (GitHub App / CI at scale):**
The CLI itself stays stateless - no changes needed. The GitHub App layer is a thin webhook receiver that shells out to `driftguard check --format json` in a worker process. Horizontal scaling is trivial because there is no shared mutable state. Bottleneck at 10x is TS parsing time for large monorepos - mitigation is to scope the TypeScript parser to changed files using `git diff --name-only` input.

**What changes at SaaS scale:**
- Add Postgres for drift result history (append-only table)
- Add a Next.js dashboard (read-only queries, no real-time requirements)
- The analysis engine itself does not change - it stays a stateless library

## Data model

The canonical type system is the core abstraction. All three parsers translate their native types into `CanonicalType` before comparison.

```
CanonicalType (discriminated union)
  | { kind: "scalar"; base: "string" | "number" | "boolean" | "date" | "bytes" | "json" | "unknown" }
  | { kind: "array"; items: CanonicalType }
  | { kind: "object"; properties: Record<string, FieldShape> }
  | { kind: "ref"; name: string }
  | { kind: "union"; types: CanonicalType[] }
  | { kind: "null" }

FieldShape
  type: CanonicalType
  nullable: boolean        // field can be null
  optional: boolean        // field can be absent from the object
  rawType: string          // original string ("String?", "string | null", "format: email")
  notes: string[]          // e.g. ["format:email", "@default(now())"]

SourceLocation
  file: string             // absolute path
  line: number
  column: number

FieldDefinition
  name: string
  shape: FieldShape
  source: "prisma" | "openapi" | "typescript"
  location: SourceLocation

EntityDefinition
  name: string             // normalized to PascalCase
  fields: FieldDefinition[]
  source: "prisma" | "openapi" | "typescript"
  location: SourceLocation

EntitySlot                 // one entity as seen from all sources
  canonicalName: string
  prisma?: EntityDefinition
  openapi?: EntityDefinition
  typescript?: EntityDefinition

EntityMap
  slots: Record<string, EntitySlot>
  scannedAt: string        // ISO8601
  sourceFiles: {
    prisma?: string
    openapi?: string
    typescript: string[]
  }

DriftIssue
  id: string               // deterministic hash for deduplication
  entity: string           // canonical entity name
  field: string | null     // null for entity-level issues (e.g. entity missing from one source)
  kind: "missing-in-source" | "type-mismatch" | "nullability-mismatch" | "entity-not-in-source"
  affectedSources: ("prisma" | "openapi" | "typescript")[]
  presentIn: ("prisma" | "openapi" | "typescript")[]
  details: Record<string, { rawType: string; shape: FieldShape }>  // keyed by source
  severity: "error" | "warning"
  message: string          // human-readable, no em dash
  location?: SourceLocation  // primary location for GitHub annotation

DriftReport
  scannedAt: string        // ISO8601
  configPath: string | null
  sourceFiles: EntityMap["sourceFiles"]
  entitiesChecked: string[]
  issues: DriftIssue[]
  summary: {
    total: number
    errors: number
    warnings: number
    byKind: Record<DriftIssue["kind"], number>
    byEntity: Record<string, number>
  }
  exitCode: 0 | 1

DriftGuardConfig
  prisma: string | null          // path to schema.prisma, null = auto-discover
  openapi: string | null         // path to openapi.yaml/json, null = auto-discover
  typescript: {
    tsconfig: string | null      // null = auto-discover
    include: string[]            // glob patterns, default ["src/**/*.ts"]
    exclude: string[]            // default ["**/*.test.ts", "**/*.spec.ts"]
  }
  entities: Record<string, {     // name aliases when TS name differs from Prisma/OpenAPI
    prisma?: string
    openapi?: string
  }>
  ignore: string[]               // "Entity.field" or "Entity.*" patterns
  severity: {
    "missing-in-source": "error" | "warning" | "off"
    "type-mismatch": "error" | "warning" | "off"
    "nullability-mismatch": "error" | "warning" | "off"
    "entity-not-in-source": "error" | "warning" | "off"
  }
  sources: ("prisma" | "openapi" | "typescript")[]  // which sources to include, default all
```

**Type normalization rules (documented, not just implemented):**

| Prisma | TypeScript | OpenAPI | Canonical |
|---|---|---|---|
| `String` | `string` | `type: string` | `scalar:string` |
| `String` | `string` | `type: string, format: email` | `scalar:string` (note: `format:email`) |
| `Int` | `number` | `type: integer` | `scalar:number` |
| `Float` | `number` | `type: number` | `scalar:number` |
| `Boolean` | `boolean` | `type: boolean` | `scalar:boolean` |
| `DateTime` | `Date` | `type: string, format: date-time` | `scalar:date` |
| `Json` | `unknown` or `Record<string,any>` | `type: object` (no properties) | `scalar:json` |
| `Bytes` | `Buffer` | `type: string, format: byte` | `scalar:bytes` |
| `T?` | `T \| null` | `nullable: true` | nullable flag |
| (not in Prisma) | `T \| undefined` | (absent from required) | optional flag |

## API contract (SOURCE OF TRUTH)

### 1. CLI interface

```
driftguard check [options]

Options:
  --config <path>           Path to driftguard.config.ts or .json
                            Default: auto-discover in cwd and parent dirs
  --prisma <path>           Override prisma schema path
  --openapi <path>          Override openapi spec path
  --tsconfig <path>         Override tsconfig path
  --include <glob>          TypeScript include glob (repeatable)
  --entity <name>           Check a specific entity only (repeatable)
  --format <text|json|github-annotations>
                            Output format (default: text)
  --severity <error|warning|all>
                            Minimum severity to report (default: all)
  --no-exit-code            Always exit 0 (useful for advisory-only runs)
  --cache / --no-cache      Enable parse cache (default: --cache)
  --cache-dir <path>        Cache directory (default: node_modules/.cache/driftguard)
  --sources <list>          Comma-separated sources to include (default: prisma,openapi,typescript)

Exit codes:
  0   No drift found (or --no-exit-code set)
  1   Drift issues found at error severity
  2   Parse/config error (malformed spec, missing file)

driftguard serve [options]

Options:
  --transport <stdio|sse>   MCP transport (default: stdio)
  --port <number>           Port for SSE transport (default: 3333)
  --config <path>           Same as check --config
  --watch / --no-watch      Watch source files and invalidate cache (default: --watch)
```

### 2. JSON output schema (`--format json`)

```typescript
// Response envelope for driftguard check --format json
// Written to stdout; stderr receives parse warnings
interface CheckOutput {
  version: "1"                    // schema version for forward compat
  report: DriftReport             // full report as defined in data model
}
```

All field names use `camelCase`. The `version` field allows consumers to detect breaking schema changes.

### 3. GitHub Annotations output (`--format github-annotations`)

Writes `::error` / `::warning` annotations to stdout using the GitHub Actions workflow commands format:

```
::error file={location.file},line={location.line},col={location.column},title=DriftGuard::{message}
::warning file={location.file},line={location.line},col={location.column},title=DriftGuard::{message}
```

When `location` is null (entity exists in no source file on disk), omit the `file`/`line`/`col` segments.

### 4. Programmatic API (Node.js library)

```typescript
// Entry point: import { check, buildEntityMap, loadConfig } from 'driftguard'

// Load and validate config
function loadConfig(options?: {
  configPath?: string
  cwd?: string
  overrides?: Partial<DriftGuardConfig>
}): Promise<DriftGuardConfig>
// Throws: ConfigValidationError (extends Error, code: "CONFIG_INVALID")
// Throws: ConfigNotFoundError (extends Error, code: "CONFIG_NOT_FOUND") - only if configPath explicitly given

// Build entity map from all sources
function buildEntityMap(config: DriftGuardConfig): Promise<EntityMap>
// Throws: ParseError (extends Error, code: "PARSE_ERROR", source: "prisma"|"openapi"|"typescript", file: string)

// Run drift check
function check(config: DriftGuardConfig): Promise<DriftReport>
// Never throws; parse errors become DriftIssue entries with kind "parse-error"

// Run drift check for a single entity
function checkEntity(entityName: string, config: DriftGuardConfig): Promise<DriftReport>
// Returns report scoped to that entity; issues array may be empty
```

### 5. MCP tool interface

Tools are exposed when running `driftguard serve`. The MCP server name is `"driftguard"`.

**Tool: `check_drift`**
```
Description: Run a full drift check across OpenAPI spec, TypeScript types, and Prisma schema. Returns a structured report of mismatches. Call this before writing or editing any API endpoint, type definition, or database model.

Input schema:
{
  "entity": string | undefined,   // optional - scope to one entity by name
  "severity": "error" | "warning" | "all" | undefined  // default "all"
}

Output schema:
{
  "hasIssues": boolean,
  "issueCount": number,
  "errorCount": number,
  "warningCount": number,
  "issues": Array<{
    "entity": string,
    "field": string | null,
    "kind": string,
    "message": string,
    "presentIn": string[],
    "affectedSources": string[]
  }>,
  "summary": string   // human-readable 1-2 sentence summary
}
```

**Tool: `get_entity_map`**
```
Description: Return the parsed entity map showing how each entity is defined across all three sources. Useful for understanding what fields exist and where.

Input schema:
{
  "entity": string | undefined   // optional - scope to one entity
}

Output schema:
{
  "entities": Record<string, {
    "prisma": { "fields": Array<{ "name": string, "rawType": string, "nullable": boolean, "optional": boolean }> } | null,
    "openapi": { "fields": Array<{ "name": string, "rawType": string, "nullable": boolean, "optional": boolean }> } | null,
    "typescript": { "fields": Array<{ "name": string, "rawType": string, "nullable": boolean, "optional": boolean }> } | null
  }>
}
```

**Tool: `list_entities`**
```
Description: List all entity names discovered across all sources.

Input schema: {}

Output schema:
{
  "entities": Array<{
    "name": string,
    "sources": string[],   // which sources define this entity
    "hasDrift": boolean
  }>
}
```

## Tradeoff analysis

**Decision 1: Single package vs monorepo**

Considered: Turborepo monorepo with `packages/core`, `packages/cli`, `packages/mcp`, `packages/action`. Clean separation of concerns, each package publishable independently.

Chosen: Single package with clean internal module boundaries (`src/parsers/`, `src/engine/`, `src/mcp/`).

Why: A monorepo adds meaningful build complexity for a first publish. The module boundaries inside `src/` are strict enough that extraction to separate packages is a one-day refactor when the CLI, MCP server, and programmatic API diverge in their release cadences. The 5-day build timeline makes the simpler path the right path. The internal API contract (the `src/index.ts` programmatic API) is designed to be the stable surface that a future `packages/core` would expose unchanged.

---

**Decision 2: Configuration required vs convention over configuration**

Considered: Require a `driftguard.config.ts` file before running. Explicit, no surprises, no brittle file discovery.

Chosen: Auto-discovery by default, config file optional as an escape hatch.

Why: The primary use case is `npx driftguard check` with zero setup, competing with the frictionless onboarding of tools like `prettier` and `eslint`. Auto-discovery covers the 80% case (standard Prisma + OpenAPI projects). The config file covers the 20% case (monorepos, non-standard paths, entity name aliases). Discovery logic is isolated in `src/config/discovery.ts` and tested independently - if it produces a wrong guess, the user overrides it with a flag or config file. The discovery function documents its search order in its JSDoc comment so it is not a black box.

---

**Decision 3: How to handle entities that exist in only one or two sources**

Considered: Only report drift for entities present in all three sources. Rationale: if something is only in Prisma, it might be an internal model not exposed via API, and reporting it as drift is noise.

Chosen: Report `entity-not-in-source` at `warning` severity by default when an entity is present in two sources but absent from a third. Do NOT report when an entity is in only one source.

Why: The sweet spot between noise and signal. An entity in Prisma and OpenAPI but not in TypeScript types is almost always a real drift (a developer added an endpoint without updating the type file). An entity only in Prisma is likely an internal-only table and reporting it would flood CI with false positives. The two-of-three threshold is configurable via severity settings. This decision is documented in the README with examples so developers know exactly what triggers a warning.
