# Backend Notes - Receipts.dev

## How to install and run

### Prerequisites
- Python 3.12.x
- PostgreSQL 16 with pgvector extension (`pgvector/pgvector:pg16` Docker image has it pre-installed)
- Redis 7
- Docker and Docker Compose (recommended)

### Docker Compose (recommended path)

```
# 1. Copy and fill in the env file
cp output/api/.env.example output/api/.env
# Edit output/api/.env with your real values

# 2. Start all services
cd output
docker compose up --build
```

Services started:
- `postgres` - pgvector-enabled PostgreSQL 16 on port 5432
- `redis` - Redis 7 on port 6379
- `api` - FastAPI on port 8000 (runs `alembic upgrade head` on startup before uvicorn)
- `worker` - Celery worker (4 concurrent processes)

### Manual development setup

```
cd output/api
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# Copy and edit env
cp .env.example .env
# Edit .env

# Run migrations (requires Postgres to be running)
alembic upgrade head

# Start API
uvicorn app.main:app --reload --port 8000

# In a second terminal, start Celery worker
celery -A app.workers.celery_app worker --loglevel=info --concurrency=2
```

## GitHub OAuth App setup

Create at https://github.com/settings/developers:
- Homepage URL: `http://localhost:3000`
- Authorization callback URL: `http://localhost:8000/api/v1/auth/github/callback`

## Contract decisions made explicit

### Token encryption
The `github_access_token` column stores Fernet-encrypted tokens. The Fernet key is derived at runtime by taking the SHA-256 hash of `SECRET_KEY` and base64-URL-encoding the 32-byte digest. No separate `FERNET_KEY` env var is needed. Changing `SECRET_KEY` will invalidate all stored tokens - users will need to re-authenticate.

### JWT cookie
On OAuth callback the backend sets `receipts_token` as an `httpOnly` cookie (SameSite=Lax). The frontend also receives the JWT indirectly through this cookie. The `secure` flag is set to `True` when `FRONTEND_URL` does NOT start with `http://localhost`.

### Alembic + pgvector column
The `diff_chunks.embedding vector(1536)` column is added via raw `ALTER TABLE` DDL in migration 0001 because SQLAlchemy's standard DDL generation does not support pgvector's `vector(N)` type syntax. The `pgvector.sqlalchemy.Vector` type is used in the ORM model and is understood by the asyncpg driver at query time.

The ivfflat index with `lists=100` is created empty in the migration. PostgreSQL will build it incrementally as rows are inserted.

### Celery + asyncio bridge
The Celery task `index_user_repos` uses `asyncio.run()` to bridge into the async service layer (GitHub client, embeddings, extractor). Each task invocation creates its own async engine + session factory with a small connection pool (3+2) and disposes it on completion. This is intentional - Celery workers run in separate processes and must not share connection pools with the FastAPI server.

### Skill extraction and evidence linking
The extractor is called once per commit (not per chunk) with up to 8 chunks from that commit in the prompt. All chunks from the commit are linked as evidence for any skills extracted from that commit. This means a skill may have many evidence chunks, not just the ones that literally contain the skill - this is by design, as it provides broad context for the recruiter chat.

Skill labels are deduplicated by exact string match across all commits in a repo. If the same label appears across repos, the `SkillEvidence` row is updated with a rolling average confidence.

### Chat rate limiting
The rate limiter uses a fixed window (not sliding) keyed on `chat:{session_id}:hour`. The TTL is set on the first increment. This means the window resets from the time the first message was sent, not from the current time. This is acceptable for MVP.

### `GET /profiles/{slug}/skills` when not indexed
Returns `409 PROFILE_NOT_INDEXED` (not 200 with empty list) so the frontend can differentiate between "indexing in progress" and "no skills found after indexing". The `indexing_status` field in the error body tells the frontend what the current job status is.

### Chat `has_evidence: false` path
When pgvector retrieval returns zero chunks above the 0.70 cosine similarity threshold, the LLM is NOT called. The response is returned immediately with `content = "No evidence found in the indexed commits for this query."` and `citations = []`. This saves OpenAI tokens and ensures the response is honest about the lack of evidence.

### Security: Hallucinated citations
The chat service validates that every `chunk_id` in the LLM's `cited_chunk_ids` response exists in the provided context window. Hallucinated IDs are stripped and a warning is logged. The answer text is still returned; only the citations list is sanitized.
