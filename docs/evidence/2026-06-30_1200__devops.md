Services:
- **web** (Next.js 15): port 3000 - public-facing frontend and SSR profile pages
- **api** (FastAPI/uvicorn): port 8000 - REST API, GitHub OAuth, JWT auth
- **worker** (Celery): internal - background indexing pipeline
- **postgres** (pgvector/pg16): port 5432 - primary datastore + vector search
- **redis** (Redis 7): port 6379 - Celery broker, rate limiting, repo cache

## Deployment Workflow

1. Developer pushes to a feature branch
2. CI runs: backend lint + type-check + migration, frontend type-check + lint + build, Docker image builds
3. PR merged to `main`
4. CI builds Docker images tagged with `$GITHUB_SHA`
5. Images pushed to registry (Docker Hub or GHCR)
6. Deploy to VPS/cloud: `docker compose pull && docker compose up -d`
7. Alembic migrations run automatically on api startup before uvicorn starts

## CI/CD Pipeline

See `.github/workflows/ci.yml`. Stages:

| Stage | Trigger | What it does |
|---|---|---|
| backend-test | push / PR | Python lint (ruff), mypy type-check, alembic migrations on test DB |
| frontend-test | push / PR | TypeScript type-check, ESLint, `next build` |
| docker-build | push to main | Builds both images with layer caching (GHA cache backend) |

## Monitoring Strategy

**Key metrics to watch:**
- `api` response time p99 (especially `GET /profiles/{slug}/skills` - the hot public path)
- Celery queue depth: spike means indexing backlog
- `worker` error rate: failed indexing jobs surface as `is_indexed=true, zero_vector_count>0`
- PostgreSQL connection pool saturation
- Redis memory usage (repo cache + rate limit keys)

**Alert conditions:**
- `api` error rate > 1% on 5xx responses
- Celery queue depth > 50 jobs for > 5 minutes
- PostgreSQL p99 query time > 500ms
- Any process OOM kill (stale `running` indexing jobs are the symptom)

**Logging:** JSON structured logs via `structlog` on the API. Celery worker logs include `job_id`, `user_id`, `repo_full_name` on every record.

## Production Deployment Checklist

- [ ] `SECRET_KEY` set to a 64-char random hex string (`openssl rand -hex 32`)
- [ ] `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` from a GitHub OAuth App
- [ ] `OPENAI_API_KEY` set
- [ ] `DATABASE_URL` pointing to production PostgreSQL with `pgvector` extension
- [ ] `REDIS_URL` pointing to production Redis
- [ ] `FRONTEND_URL` set to production domain (e.g. `https://receipts.dev`)
- [ ] `GITHUB_CALLBACK_URL` set to `https://receipts.dev/api/v1/auth/github/callback`
- [ ] `INTERNAL_API_URL=http://api:8000` set on the `web` service (Docker SSR routing)
- [ ] Health check endpoints verified (`GET /health` returns 200)
- [ ] Alembic migrations run (`alembic upgrade head`) before deploy
- [ ] Rollback plan: keep previous Docker image tag, redeploy with prior tag + `down` migrations
- [ ] pgvector extension enabled on production DB (`CREATE EXTENSION IF NOT EXISTS vector`)
- [ ] Redis `maxmemory-policy` set to `allkeys-lru` to prevent OOM
- [ ] SSL/TLS terminated at reverse proxy (nginx or Caddy) - do not expose api/web directly on 80/443
- [ ] Monitoring configured and alerting tested

## Scaling Notes

**What breaks first under load:**
1. **pgvector ivfflat index** - becomes the bottleneck at ~100k vectors. Tune `lists` parameter from 100 to `sqrt(rows)`. At 1M+ vectors, migrate to HNSW index type.
2. **Celery worker concurrency** - default `--concurrency=4`. Each task is I/O-bound (GitHub API + OpenAI API). Can safely run 8-16 concurrent tasks on a single worker; add more worker containers horizontally.
3. **FastAPI workers** - `--workers 2` in Docker is conservative. Scale to `2 * CPU_cores + 1` (gunicorn rule).
4. **PostgreSQL connection pool** - async SQLAlchemy pool defaults to 5 connections per process. With 2 uvicorn workers + 16 Celery tasks, peak is ~34 connections. Set `pool_size=10, max_overflow=20`.
5. **Redis rate-limit keys** - 1000 active users * 20 messages/hour * 24h = 480k keys/day. Each key is tiny (<100 bytes). No bottleneck until millions of users.

**Horizontal scaling path:**
- `web`: stateless, add more containers behind a load balancer
- `api`: stateless (JWT auth, no server-side session), add more containers
- `worker`: stateless, add more containers (Celery auto-distributes from Redis queue)
- `postgres`: vertical scale first (read replicas for public profile reads at scale)
- `redis`: single instance is fine until 10k+ concurrent users

## Local Development Quick Start

```bash
git clone <repo>
cd receipts-dev/output

# Set env vars
cp api/.env.example api/.env
# Edit api/.env with your GitHub OAuth app credentials and OpenAI key

# Start all services
docker compose up --build

# Frontend: http://localhost:3000
# API docs: http://localhost:8000/docs
```
