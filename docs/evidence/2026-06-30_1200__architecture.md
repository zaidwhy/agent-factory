# Architecture: Receipts.dev

## Stack

- **Backend** - FastAPI 0.111 (Python 3.12) with uvicorn - async-first, Pydantic v2 native, clean separation between HTTP layer and service logic
- **Background jobs** - Celery 5.4 with Redis 5.0 as broker and result backend - diff indexing is long-running (seconds to minutes per user); Celery decouples indexing from the HTTP request and lives in the same Python codebase as the services it calls, avoiding a separate Node.js worker process
- **Database** - PostgreSQL 16 + pgvector 0.7 extension - relational structure for users/repos/skills, vector column on diff_chunks for similarity search without a separate vector service (Pinecone adds cost and an extra failure point at MVP scale)
- **ORM / migrations** - SQLAlchemy 2.0 (async, asyncpg driver) + Alembic 1.13 - async sessions match FastAPI's event loop; Alembic provides deterministic schema history
- **LLM** - OpenAI API: `gpt-4o-mini` for skill extraction (low cost, high throughput), `gpt-4o` for recruiter chat (quality matters there), `text-embedding-3-small` for 1536-dim vectors - all behind a thin service interface so the model can be swapped without touching routers
- **GitHub integration** - httpx 0.27 (async) against GitHub REST API v3 - covers the specific endpoints needed (commits, files with patches, user repos) without the weight of PyGitHub
- **Frontend** - Next.js 15 (App Router) + TypeScript 5.4 - public profile pages are the product's shareable artifact; they need SSR for recruiter-facing SEO, per-page OG meta tags, and Incremental Static Regeneration to serve cached profiles at Vercel edge without a hot DB read on every pageview; React/Vite cannot do this without manual SSR plumbing
- **Styling / components** - Tailwind CSS 3.4 + shadcn/ui - unstyled primitives copied into the repo, no component library runtime dependency
- **Client state / data fetching** - TanStack Query 5.45 - handles stale-while-revalidate, background polling for indexing status, and per-query error boundaries
- **Auth tokens** - python-jose 3.3 (backend) generating HS256 JWTs, stored in the browser as httpOnly cookie set by the backend on the OAuth callback redirect

## Scalability notes

**Indexing path (write-heavy, async)**

At MVP, indexing runs as a single Celery task per user. At 10x load, Celery workers scale horizontally behind the same Redis broker with no code changes. The bottleneck shifts to GitHub API rate limits (5,000 requests/hour per OAuth token) and OpenAI embedding throughput. Mitigations already baked into the design: commits and their raw diffs are written to Postgres on first fetch and never re-fetched (commit SHAs are content-addressed and immutable); embedding calls are batched in groups of 100 chunks per API call; the index caps at `MAX_REPOS=20` and `MAX_COMMITS_PER_REPO=500` per user, enforced in the Celery task. Stretch: webhook-based incremental re-index (GitHub `push` event) replaces full re-index.

**Read path (profile pages + recruiter chat)**

Public profile pages are SSR'd once and then served from Vercel Edge Cache (ISR with `revalidate=3600`). A revalidation tag is invalidated when indexing finishes, so new profiles appear without manual purge. The read path has no hot DB reads at steady state.

Each recruiter chat message triggers one pgvector cosine similarity search filtered by `user_id`, one OpenAI embedding call, and one chat completion call. At 10x: add a Redis cache keyed on `sha256(query + user_id)` with 24-hour TTL for identical questions; rate-limit the chat endpoint at 20 messages/session/hour (Redis counter, already in the design). The pgvector `ivfflat` index with `lists=100` handles up to ~1M vectors per partition efficiently; beyond that, switch to `hnsw` index or partition by `user_id` range.

**Database growth**

At 1M users x 500 chunks average = 500M rows in `diff_chunks`. pgvector's HNSW index degrades gracefully but at that scale a dedicated vector store (Pinecone or Weaviate) becomes the right call. The service interface for `retriever.py` is the only file that changes - routers and chat logic are unaffected.

**Caching summary**

| Layer | What | TTL |
|---|---|---|
| Postgres | Raw diff patch text, embeddings | Permanent (immutable) |
| Redis | GitHub API repo list per user | 1 hour |
| Redis | Chat rate-limit counters | 1 hour rolling |
| Redis | Identical chat answers (sha256 key) | 24 hours |
| Vercel Edge | Rendered public profile pages (ISR) | 1 hour, invalidated on index complete |

## API contract (SOURCE OF TRUTH - engineers must not deviate)

**Base URL**: `http://localhost:8000` in development. All paths are prefixed with `/api/v1`.

**Authentication**: Endpoints marked `[auth]` require an `Authorization: Bearer <jwt>` header. The JWT is a HS256 token signed with `SECRET_KEY`, containing `{ "sub": "<user_uuid>", "exp": <unix_timestamp> }`. Token lifetime: 7 days.

**Error envelope** (all 4xx/5xx responses use this shape):
```json
{ "detail": "Human-readable message", "code": "SNAKE_CASE_ERROR_CODE" }
```

### Auth

#### `GET /api/v1/auth/github`
Initiates GitHub OAuth. Backend builds the GitHub authorization URL with a CSRF state token stored in Redis for 10 minutes, then returns a redirect (302) to GitHub.

- Request: none (no body, no query params)
- Response: HTTP 302 redirect to `https://github.com/login/oauth/authorize?client_id=...&redirect_uri=...&scope=read:user,repo&state=<random_hex_32>`
- Errors: none expected

---

#### `GET /api/v1/auth/github/callback`
GitHub calls this after user approves. Backend exchanges the code for a GitHub access token, upserts the user, issues a JWT, sets it as an httpOnly cookie named `receipts_token` (SameSite=Lax, Secure in production), then HTTP 302 redirects to `FRONTEND_URL/auth/callback?status=ok`.

- Request (query params):
  ```
  code:  string  - temporary code from GitHub
  state: string  - must match what was stored in Redis
  ```
- Response: HTTP 302 redirect to frontend with cookie set
- Errors:
  - `400 BAD_OAUTH_STATE` - state mismatch or expired
  - `502 GITHUB_API_ERROR` - GitHub token exchange failed

---

### Indexing

#### `POST /api/v1/index` [auth]
Enqueues a Celery indexing task for the authenticated user. Only one job may be active per user at a time.

- Request body (JSON):
  ```json
  {
    "repo_full_names": ["string"] 
  }
  ```
  `repo_full_names`: optional array of `"owner/repo"` strings to restrict which repos are indexed. If omitted or empty array, indexes all non-archived repos up to `MAX_REPOS` limit.

- Response `202`:
  ```json
  {
    "job_id": "uuid",
    "status": "queued"
  }
  ```
- Errors:
  - `401 UNAUTHORIZED`
  - `409 INDEX_ALREADY_RUNNING` - a job with status `queued` or `running` already exists for this user
  - `422 VALIDATION_ERROR` - request body malformed

---

#### `POST /api/v1/chat/sessions/{session_id}/messages`
Sends a user message and returns the AI assistant's grounded response. This is synchronous. The pipeline: embed query -> pgvector search (top 8 chunks, threshold cosine similarity > 0.70, filtered by profile user_id) -> build context -> call gpt-4o with grounding system prompt -> parse structured response.

If no chunks meet the similarity threshold, the assistant responds with `has_evidence: false` and does not call the chat LLM.

- Path param: `session_id`
- Header: `X-Session-Token: <session_token>` (required - validates the caller owns this session)
- Request body (JSON):
  ```json
  {
    "content": "string"
  }
  ```
  Max `content` length: 500 characters.

- Response `200`:
  ```json
  {
    "message": {
      "id": "uuid",
      "role": "assistant",
      "content": "string",
      "citations": [
        {
          "chunk_id": "uuid",
          "file_path": "string",
          "start_line": "number",
          "end_line": "number",
          "commit_sha": "string",
          "repo_full_name": "string",
          "github_permalink": "string",
          "snippet": "string"
        }
      ],
      "has_evidence": "boolean",
      "created_at": "ISO8601"
    }
  }
  ```
  When `has_evidence` is false, `citations` is an empty array and `content` is exactly `"No evidence found in the indexed commits for this query."`.

- Errors:
  - `401 INVALID_SESSION_TOKEN` - session token doesn't match session_id
  - `404 SESSION_NOT_FOUND`
  - `410 SESSION_EXPIRED` - session has passed its `expires_at`
  - `422 VALIDATION_ERROR` - content too long or empty
  - `429 RATE_LIMITED` - 20 messages per session per hour exceeded

---

## Tradeoff analysis

### 1. GitHub OAuth from day one vs. username-only input for MVP

The idea suggests "public username for MVP, OAuth later." This was rejected. The entire value proposition of Receipts.dev is verified authorship - a recruiter must be able to trust that the indexed commits were authored by the person claiming them. A username-only flow lets anyone generate a "receipts" profile for any developer, which actively undermines the trust signal and creates a content moderation problem. GitHub OAuth adds approximately 2 hours of backend work and zero frontend work (it is a redirect). The decision: OAuth from the start, with the public repos scope only (no private repo access needed for MVP), keeping the permission ask minimal.

### 2. Celery + Redis vs. BullMQ (Node.js queue) for background indexing

The idea explicitly mentions BullMQ. BullMQ requires a separate Node.js worker process, which means maintaining two runtimes (Python and Node.js) in the same service boundary. The indexing pipeline (chunking, embedding, LLM extraction) is implemented in Python because the relevant libraries (openai, tiktoken, pgvector-python, tenacity, httpx) are all Python-native. Running that logic from a BullMQ worker would require either HTTP calls from Node.js to Python services (added latency, added failure point) or re-implementing the pipeline in TypeScript (doubled code). Celery runs in the same Python process as the services it calls, uses the same DB session factory, and is a battle-tested queue for exactly this kind of ML-pipeline workload. The decision: Celery + Redis.

### 3. Next.js 15 (App Router) vs. React + Vite

The default in these operating rules is React + Vite. Next.js was chosen because the shareable public profile page - the primary artifact the developer puts on their resume - has hard requirements that React/Vite cannot satisfy without significant manual infrastructure: server-side OG meta tag generation per profile (so `og:title` and `og:description` show the right candidate name when a recruiter pastes the link into Slack), server-side data fetching for the initial skill graph (no spinner on first load when a recruiter visits the page cold), and Incremental Static Regeneration to serve cached profile pages at Vercel's edge without a DB hit per pageview. These are not nice-to-haves - they are the mechanism by which the profile link feels like a polished professional artifact rather than a developer toy. The decision: Next.js 15 App Router, with all non-SSR UI (chat, dashboard) implemented as standard client components.
```
