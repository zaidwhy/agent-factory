# DevOps - DriftGuard Infrastructure

---

## Infrastructure Architecture

### Containerization

**Stack:** Node.js 20 Alpine + Docker multi-stage build

**Image:** `driftguard:latest` built from `./Dockerfile`

**Build strategy:**
- Stage 1 (Builder): Installs all dependencies (dev + prod), runs `npm run build` to produce `dist/` directory
- Stage 2 (Runner): Minimal Alpine image with only production dependencies + built artifacts
- Layer caching: `package.json` / `package-lock.json` cached separately from source code

**Artifact outputs:**
- `dist/index.js` - ESM entry point (programmatic API)
- `dist/index.cjs` - CommonJS entry point
- `dist/index.d.ts` - TypeScript type definitions
- `dist/cli/index.js` - CLI entry point (Node shebang)

**Image size:** ~380MB (base alpine 70MB + node 140MB + node_modules 170MB)

---

### Local Development Container

**File:** `docker-compose.yml`

**Service:** `driftguard-mcp`

**Purpose:** Run DriftGuard as an MCP server in SSE mode so Claude Code / Cursor clients can connect without installing locally.

**Volume mounts:**
- `${PROJECT_ROOT:-.}:/workspace:ro` - Project to analyze (read-only)
- `driftguard-cache:/cache/driftguard` - Parse cache (survives restarts)

**Networking:**
- Port `3333` - MCP SSE transport (configurable via `DRIFTGUARD_PORT`)
- Clients connect: `http://localhost:3333/sse`

**Environment variables:**
- `PROJECT_ROOT` - Absolute path to project to analyze (defaults to `.`)
- `DRIFTGUARD_LOG_LEVEL` - Log verbosity: `debug`, `info` (default), `warn`, `error`
- `DRIFTGUARD_NO_COLOR` - Disable ANSI colors in logs (set to `"1"`)
- `DRIFTGUARD_CACHE_DIR` - Cache directory path (defaults to `/cache/driftguard`)

**Resource limits:**
- Memory: 512MB limit, 128MB reservation
- CPU: Unrestricted (will auto-scale within docker engine limits)

**Health check:**
- TCP connect probe on port 3333, every 30s, 15s start grace period, 3 retries
- When unhealthy: container restarts automatically (restart: unless-stopped)

## Deployment Workflows

### Local MCP Server (Development / CI Integration)

```bash
# Start the server
export PROJECT_ROOT=/path/to/your/project
docker compose up -d

# Tail logs
docker compose logs -f driftguard-mcp

# Run a check via the server
curl -X POST http://localhost:3333/sse \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/call",
    "params": {
      "name": "check_drift",
      "arguments": {"severity": "error"}
    }
  }'

# Stop
docker compose down
```

### CLI One-Shot Execution (Stateless CI)

```bash
# Check and exit with JSON output
docker run --rm \
  -v /my/project:/workspace \
  driftguard:latest check --format json

# Check with explicit paths
docker run --rm \
  -v /my/project:/workspace \
  driftguard:latest check \
    --prisma /workspace/prisma/schema.prisma \
    --openapi /workspace/openapi.yaml \
    --format github-annotations

# Check specific entity
docker run --rm \
  -v /my/project:/workspace \
  driftguard:latest check --entity User --severity error
```

### GitHub Actions Workflow (CI/CD)

**File:** `.github/workflows/ci.yml`

**Trigger events:**
- Push to `main` or `develop` branches
- Pull requests to `main`
- Tag push matching `v*` (e.g., `v0.2.0`)

**Concurrency:** In-progress runs are cancelled on new push (except `main` branch)

**Jobs:**

1. **Lint** (6 min)
   - TypeScript type check: `npm run typecheck`
   - ESLint: `npm run lint`
   - Prettier format check: `npm run format:check`

2. **Security** (2 min)
   - `npm audit --audit-level=high --omit=dev`
   - Fails if high/critical CVEs found in prod dependencies

3. **Test** (10 min, matrix: Node 20.x + 22.x)
   - Coverage run on Node 20 only: `npm run test:coverage`
   - Compatibility run on Node 22: `npm test`
   - Coverage artifact uploaded (14-day retention)

4. **Build** (5 min, depends on lint + test)
   - `npm run build` - produces ESM + CJS + .d.ts
   - Verify output files exist
   - Smoke test CLI: `--help`, `check --help`, `serve --help`
   - Inspect package contents (dry run npm pack)
   - Upload dist/ artifact (7-day retention)

5. **Publish to npm** (3 min, only on version tags)
   - Depends on: `build` + `security`
   - Triggers only on: `refs/tags/v*`
   - Requires: `NPM_TOKEN` secret in repository Settings > Secrets
   - Verifies `package.json` version matches git tag
   - Publishes with npm provenance (SLSA supply-chain attestation)

**Timing:** Full CI pipeline (lint -> test matrix -> build -> publish) ~25 minutes

## CI / CD Pipeline

### Pre-Commit (Local)

Optional setup for developers to run checks before pushing:

```bash
# Install husky + lint-staged (optional)
npm install -D husky lint-staged

# Initialize git hooks
npx husky install

# Configure .husky/pre-commit
npx husky add .husky/pre-commit 'npx lint-staged'

# Add to package.json
{
  "lint-staged": {
    "src/**/*.ts": ["eslint --fix", "prettier --write"],
    "tests/**/*.ts": ["eslint --fix", "prettier --write"]
  }
}
```

### Post-Merge (GitHub Actions)

Automatically runs when PR is merged to `main`:

1. Checkout code
2. Install dependencies (npm ci with cached node_modules)
3. Run linting, type check, security audit
4. Run full test suite (coverage + matrix)
5. Build all output formats
6. Publish to npm registry (if tag matches version)

### Environment Variables (Secrets)

Set in repository Settings > Secrets and Variables > Actions:

- `NPM_TOKEN` - npm registry authentication token (for publish job)

## Monitoring Strategy

### Container Health

**Method:** TCP connect health check (port 3333)

**Interval:** 30 seconds

**Threshold:** 3 consecutive failures -> container restart

**Logs:** Docker json-file driver with rotation (10MB max per file, 3 files max)

### Application Logging

**Levels:** `debug`, `info` (default), `warn`, `error`

**Format:** JSON to stderr (structured logging in containers)

**Disable colors:** Environment variable `DRIFTGUARD_NO_COLOR=1` (reduces log noise)

**Where to send logs (deployment-specific):**
- **Local docker-compose:** `docker compose logs -f driftguard-mcp`
- **Kubernetes:** Configure container log driver to ship to centralized logging (ELK, Datadog, CloudWatch)
- **Cloud Run / Lambda:** Use provider's native logging (CloudWatch, Cloud Logging)

### Performance Monitoring

**CLI mode (stateless):**
- Measure: `time node dist/cli/index.js check`
- Expected: 2-4 seconds for 500-file TypeScript project
- Baseline: Establish in CI, track per-release

**MCP server mode (watch + cache):**
- Measure: MCP tool call latency (should be <50ms after initial parse)
- Monitor: Memory usage (parse cache grows ~5MB per 100 entities)
- Expected: Entity map stays <100MB for projects <10k entity definitions

### Alerting (Production)

If running on Kubernetes or similar:

- **CPU spike:** Parse operation is blocking event loop (usually not an issue; stateless CLI should exit quickly)
- **Memory leak:** Watch mode not invalidating cache on file deletion (rare, but monitor with long-running servers)
- **Port 3333 unreachable:** Either container crashed or MCP server failed to bind (check health check logs)

## Production Checklist

### Before First Deploy

- [ ] Code reviewed and tested locally (`npm test` passes)
- [ ] CI pipeline green on `main` branch
- [ ] Security audit clean (`npm audit` shows no high/critical)
- [ ] TypeScript strict mode enforced (`npm run typecheck` passes)
- [ ] Linting passes (`npm run lint` with no errors)
- [ ] README updated with any breaking changes
- [ ] CHANGELOG entry written if releasing
- [ ] Git tag created and pushed (triggers npm publish): `git tag v0.2.0 && git push --tags`

### Per-Release (npm publish)

- [ ] Version bump in `package.json` (follow semver)
- [ ] Git tag matches: `git tag v$(node -p "require('./package.json').version")`
- [ ] Pre-publish test gate passes: `npm test` (re-run in CI before publishing)
- [ ] npm provenance enabled: `npm publish --provenance` (automatic in CI)
- [ ] npm package page updated (README appears, no secrets visible)
- [ ] GitHub release created with changelog (manual; optional but recommended)

### Container Deployment

- [ ] Dockerfile builds without errors locally
- [ ] Image runs without root (USER driftguard set in Dockerfile)
- [ ] Health check passes within 30s of startup
- [ ] Memory limit reasonable for workload (512MB default; adjust if parsing >1k files)
- [ ] Cache volume has enough space (10GB safe default for 100k+ entities)
- [ ] Environment variables are injected at runtime (no hardcoded secrets in image)
- [ ] Logs are sent to centralized logging system (not just docker logs)

### Runtime Safety

- [ ] `DRIFTGUARD_NO_COLOR=1` set in production (cleaner logs)
- [ ] `NODE_ENV=production` set (enables optimizations, disables debug endpoints)
- [ ] `npm audit` re-run before deployment (catches new CVEs)
- [ ] Mount volumes as read-only where possible: `-v /project:/workspace:ro`
- [ ] No hardcoded config paths; always accept `--config` override or env var

### Rollback Plan

- Docker: `docker compose down && docker compose up -d` (pulls previous stable image tag)
- npm: Previous version remains available; consumers can pin version in `package.json`
- GitHub: Revert commit and push (CI re-runs, publishes new tag)

## Scaling Notes

### Vertical Scaling (Single Container)

Current resource budgets:

- **Memory:** 512MB limit
- **CPU:** Unrestricted (single-threaded Node.js; will use 1 full core)

**When to increase:**
- TS project >5k files: Increase memory to 1GB
- TS project >20k files: Increase memory to 2GB

**Implementation:**
- docker-compose: Edit `deploy.resources.limits.memory`
- Kubernetes: Edit `resources.limits.memory` in Pod spec

### Horizontal Scaling (Multiple Instances)

DriftGuard is **stateless** in CLI mode and **locally-cached** in MCP server mode. Scaling strategy depends on deployment:

#### Option 1: Load Balancer + Multiple CLI Containers (CI)

```yaml
# Kubernetes
---
kind: Job
metadata:
  name: driftguard-check
spec:
  parallelism: 4           # Run 4 pods in parallel
  completions: 4
  template:
    spec:
      containers:
      - name: driftguard
        image: driftguard:latest
        command: ["node", "/app/dist/cli/index.js", "check", "--format", "json"]
        resources:
          limits:
            memory: "512Mi"
```

#### Option 2: MCP Server Per Project (Development)

```bash
# Separate container per project analyzed
docker run -d \
  -p 3333:3333 \
  -v /project-a:/workspace:ro \
  --name driftguard-project-a \
  driftguard:latest

docker run -d \
  -p 3334:3333 \
  -v /project-b:/workspace:ro \
  --name driftguard-project-b \
  driftguard:latest
```

#### Option 3: SaaS Backend (Future)

When scaling to SaaS / API layer:

- Add Postgres database for drift result history (append-only table per organization)
- Add Next.js dashboard layer (separate service, queries Postgres)
- DriftGuard core remains stateless library (no code changes needed)
- GitHub webhook triggers stateless CLI in worker process
- Results streamed to Postgres + dashboard notified via webhooks

**Current architecture supports this without modification** because:
- Programmatic API is stable and documented (`src/index.ts`)
- Data model is JSON-serializable (DriftReport)
- No internal state or global mutable objects
- Cache is isolated per run (node_modules/.cache/driftguard)

## Troubleshooting

### Container fails to start

```bash
# Check logs
docker compose logs driftguard-mcp

# Common issues:
# - Port 3333 already in use: docker compose down; lsof -i :3333
# - Cache directory permissions: chmod 777 driftguard-cache
# - Project path doesn't exist: set PROJECT_ROOT=/valid/path
```

### Health check fails

```bash
# Manually test the health probe
docker compose exec driftguard-mcp node -e \
  "require('net').connect(3333,'127.0.0.1',()=>process.exit(0)).on('error',()=>process.exit(1))"

# If this fails, check port binding
docker compose exec driftguard-mcp netstat -tulpn | grep 3333
```

### Out of memory

```bash
# Monitor real usage
docker compose exec driftguard-mcp ps aux

# Increase memory limit in docker-compose.yml
deploy:
  resources:
    limits:
      memory: 1g
```

### Cache grows indefinitely

Cache is keyed by source file content hash. Normal behavior:

```bash
# Check cache size
du -sh driftguard-cache

# Clear cache if needed
docker volume rm driftguard-cache
docker compose up -d  # rebuilds cache
```

### npm publish fails in CI

```bash
# Verify NPM_TOKEN is set
gh secret list

# Verify version matches tag
git tag  # should show vX.Y.Z matching package.json

# Manually test publish (dry run)
npm publish --dry-run
```

## Operations Runbook

### Daily

- Monitor container restarts: `docker compose logs driftguard-mcp | grep "restart"`
- Check disk space: `df -h` (cache volume should not exceed 50% of available space)

### Weekly

- Review CI logs for flaky tests: https://github.com/zaidwhy/driftguard/actions
- Update base image: `docker pull node:20-alpine` (check for security updates)
- Run `npm audit` locally and in CI (catches new CVEs)

### Monthly

- Review performance metrics (CI build time, test execution time)
- Analyze cache hit rates (if running MCP server mode long-term)
- Update transitive dependencies: `npm update` (not major versions)

### Quarterly

- Major version updates: Node.js 20 LTS security patches, TypeScript minor updates
- Review and update this runbook based on learnings
- Performance benchmarking against new dependency versions

## Appendix: Docker Commands Reference

```bash
# Build image
docker build -t driftguard:latest -f Dockerfile .

# Run check command
docker run --rm \
  -v $(pwd):/workspace \
  driftguard:latest check --help

# Run MCP server
docker run -d \
  -p 3333:3333 \
  -v $(pwd):/workspace:ro \
  --name driftguard-server \
  driftguard:latest serve --transport sse --port 3333

# Access server logs
docker logs driftguard-server

# Stop server
docker stop driftguard-server && docker rm driftguard-server

docker compose -f docker-compose.yml up -d
```
